
# Breeder v1.0 Schema and Domain Model

Status: IMPLEMENTATION-READY PLAN  
Physical database: existing Journal Supabase project sjodccpuyaasljcunmug  
Migration authority: nickdevph/aquaticfinder-journal, first Breeder migration 025 after Journal 024 is merged

This document freezes the domain model without executing it. Names are production recommendations; the authority and invariants are mandatory.

## 1. Database conventions

- PostgreSQL public schema, logical Breeder namespace by breeder_ table prefix.
- UUID primary keys generated by the database.
- Every Breeder-owned row has owner_user_id, created_at and updated_at.
- Owner identity is the verified Core subject UUID, stored as an opaque external identity. There is no foreign key to Core.
- Child-to-parent references use composite foreign keys containing owner_user_id wherever the parent is owner-scoped.
- Parent tables expose UNIQUE(id, owner_user_id) constraints to support composite foreign keys.
- Biological history is append-only or archived. Hard delete is not a product operation.
- Mutable projections carry a revision integer. Commands use expected_revision and optimistic concurrency.
- All dates are timestamptz unless explicitly named local_date or local_time.
- Quantity columns are non-negative numeric/integer values with an explicit unit. Quantity is never silently inferred from a display string.

## 3. Foundation relations for BREEDER-FOUNDATION-001

### breeder_programs

Required fields:

~~~text
id uuid primary key
owner_user_id uuid not null
name text not null
species_key text null
species_display_name text null
reproductive_archetype text null
status text not null: ACTIVE | PAUSED | ARCHIVED
archived_at timestamptz null
revision integer not null default 1
created_at timestamptz not null
updated_at timestamptz not null
unique(id, owner_user_id)
check name is non-empty
~~~

A Program is durable context, not mandatory ceremony. The first event path may create a Program and its initiating biological record atomically in a later package.

### breeder_parentage_contexts

Required fields:

~~~text
id uuid primary key
owner_user_id uuid not null
program_id uuid not null
context_type text not null:
  EXACT_INDIVIDUALS | EXACT_PAIR | BREEDING_GROUP |
  POPULATION | SOURCE_POPULATION | UNKNOWN
evidence_status text not null:
  RECORDED | PARTIAL | UNKNOWN
label text null
notes text null
created_at timestamptz not null
updated_at timestamptz not null
unique(id, owner_user_id)
foreign key (program_id, owner_user_id)
  references breeder_programs(id, owner_user_id)
~~~

A context cannot claim exact parents unless members support that claim. Population and unknown contexts remain non-exact.

### breeder_parentage_members

Required fields:

~~~text
id uuid primary key
owner_user_id uuid not null
context_id uuid not null
journal_livestock_id uuid null
member_role text not null:
  SIRE | DAM | PARENT | GROUP_MEMBER | SOURCE_POPULATION
evidence_note text null
recorded_at timestamptz not null
unique(id, owner_user_id)
foreign key (context_id, owner_user_id)
  references breeder_parentage_contexts(id, owner_user_id)
foreign key (journal_livestock_id, owner_user_id)
  references journal_livestock(id, owner_user_id)
  on delete restrict
~~~

A missing journal_livestock_id is allowed for population/source/unknown members. No row is created merely to fill a required sire or dam slot.

### breeder_reproductive_outputs

Required fields:

~~~text
id uuid primary key
owner_user_id uuid not null
program_id uuid not null
parentage_context_id uuid not null
output_kind text not null:
  SPAWN | EGG_BATCH | COLLECTION | BROOD | RECRUITMENT | OTHER
species_key text null
source_label text null
started_at timestamptz null
collected_at timestamptz null
original_quantity numeric not null
quantity_unit text not null: EGGS | FRY | JUVENILES | RECRUITS | OTHER
status text not null: OPEN | PARTIALLY_MATERIALIZED | MATERIALIZED | HISTORICAL | CLOSED
legacy_source boolean not null default false
revision integer not null default 1
created_at timestamptz not null
updated_at timestamptz not null
unique(id, owner_user_id)
foreign keys to program and parentage context using owner composites
check original_quantity >= 0
~~~

Remaining quantity is derived from the output ledger. There is no writable remaining_quantity authority.

### breeder_hatch_observations

Required fields:

~~~text
id uuid primary key
owner_user_id uuid not null
reproductive_output_id uuid not null
observation_kind text not null:
  STRUCTURED_HATCH | SCALAR_HATCH | RECRUITMENT_OBSERVATION
observed_at timestamptz not null
quantity numeric not null
quantity_unit text not null
wetting_attempt_id uuid null
cohort_label text null
notes text null
supersedes_id uuid null
created_at timestamptz not null
unique(id, owner_user_id)
foreign key (reproductive_output_id, owner_user_id)
  references breeder_reproductive_outputs(id, owner_user_id)
  on delete restrict
check quantity >= 0
~~~

One accepted observation creates one materialization ledger entry. A corrected observation supersedes the old observation with an auditable delta; it does not silently overwrite history. A scalar legacy observation is visible and counts once, but legacy/historical outputs are barred from new positive commerce authority unless a separately qualified rule explicitly reopens them.

### breeder_offspring_groups

Required fields:

~~~text
id uuid primary key
owner_user_id uuid not null
program_id uuid not null
current_tank_id uuid null
group_label text not null
stage text not null
status text not null: ACTIVE | HISTORICAL | ARCHIVED
quantity_unit text not null
revision integer not null default 1
created_at timestamptz not null
updated_at timestamptz not null
unique(id, owner_user_id)
foreign key (program_id, owner_user_id)
  references breeder_programs(id, owner_user_id)
foreign key (current_tank_id, owner_user_id)
  references journal_tanks(id, owner_user_id)
  on delete set null
check group_label is non-empty
~~~

The current tank is mutable location context. Group identity and provenance do not change when a group moves. Tank deletion or archive cannot erase the operation snapshot.

### breeder_group_provenance

Required fields:

~~~text
id uuid primary key
owner_user_id uuid not null
offspring_group_id uuid not null
reproductive_output_id uuid null
hatch_observation_id uuid null
source_group_id uuid null
provenance_role text not null:
  PRIMARY_OUTPUT | HATCH | SPLIT_FROM | MERGED_FROM | PROMOTED_FROM
recorded_at timestamptz not null
unique(id, owner_user_id)
foreign keys use owner composites
check exactly one of reproductive_output_id,
hatch_observation_id or source_group_id is non-null
~~~

This is a typed union with real foreign keys, not an unvalidated entity_id string. A merge receives one edge per source group plus all output/hatch edges required to preserve provenance.

### breeder_group_operations

Required fields:

~~~text
id uuid primary key
owner_user_id uuid not null
operation_type text not null:
  CREATE | COUNT_REVISION | LOSS | MOVE | SPLIT | MERGE | STAGE_CHANGE
operation_at timestamptz not null
actor_user_id uuid not null
idempotency_key text not null
expected_revision integer null
primary_group_id uuid not null
notes text null
created_at timestamptz not null
unique(owner_user_id, idempotency_key)
unique(id, owner_user_id)
foreign key (primary_group_id, owner_user_id)
  references breeder_offspring_groups(id, owner_user_id)
~~~

Operation rows are append-only. A move or stage change has no quantity ledger line. A split or merge writes all affected groups in one transaction.

### breeder_quantity_ledger

Required fields:

~~~text
id uuid primary key
owner_user_id uuid not null
operation_id uuid not null
offspring_group_id uuid null
reproductive_output_id uuid null
entry_type text not null:
  OUTPUT_CREATED | OUTPUT_REMOVED | HATCH_MATERIALIZED |
  GROUP_CREATED | GROUP_IN | GROUP_OUT | LOSS
quantity_delta numeric not null
quantity_unit text not null
source_observation_id uuid null
created_at timestamptz not null
unique(id, owner_user_id)
foreign keys use owner composites
check quantity_delta <> 0
check exactly one biological owner of the entry
~~~

A transaction locks all affected output/group rows, validates non-negative resulting balances, then inserts ledger entries. Quantity read models are sums over committed ledger entries; any cached display is disposable.

### breeder_command_receipts

Required fields:

~~~text
id uuid primary key
owner_user_id uuid not null
idempotency_key text not null
command_type text not null
request_hash text not null
status text not null: COMMITTED | REJECTED
result_type text null
result_id uuid null
response_json jsonb null
created_at timestamptz not null
unique(owner_user_id, idempotency_key)
~~~

Same key plus same hash returns the original committed readback. Same key plus a different hash returns IDEMPOTENCY_CONFLICT and performs no write.

## 4. Deferred v1.0 relations

The following are planned and must use the same owner/composite-FK conventions:

- breeder_stock_membership and breeder_stock_history;
- breeder_evaluations and evidence associations;
- breeder_selection_sessions and selection members;
- breeder_dispositions;
- breeder_schedule_bindings and lifecycle suggestions;
- breeder_commerce_handoffs;
- breeder_commerce_handoff_media;
- breeder_commerce_reconciliations.

Commerce handoffs store immutable biological snapshots, proposed commerce quantity, selected public media IDs and provenance evidence. Reconciliation stores commercial allocation/outcome only. It never writes quantity ledger entries.

## 5. Journal references and delete behavior

Before adding foreign keys, the Journal migration must qualify owner-composite uniqueness for the referenced Journal relations or create equivalent validated unique indexes on:

~~~text
journal_tanks(id, owner_user_id)
journal_livestock(id, owner_user_id)
journal_media_assets(id, owner_user_id)
~~~

If an existing relation cannot safely receive the required uniqueness proof, the Breeder reference is rejected at migration review rather than downgraded to an unchecked UUID.

- current_tank_id uses ON DELETE SET NULL because tank is location context and group history retains snapshots;
- Journal livestock parent references use ON DELETE RESTRICT while active provenance depends on them; account-deletion handling is explicit and reviewed;
- biological parentage and group provenance use ON DELETE RESTRICT;
- Journal archive state is not treated as deletion;
- the Journal account-deletion service must delete or anonymize Breeder rows according to the existing retention policy without leaving cross-account readable remnants.

## 6. Rollback compatibility

025 is additive and forward-only after production data exists. On disposable databases, a tested rollback may remove the entire unreferenced breeder foundation. On data-bearing targets, rollback is feature disable plus forward repair. No migration rewrites or destructive history cleanup are admitted.
